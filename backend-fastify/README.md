# Gym Backend (Fastify + MySQL)

TypeScript/Fastify port of the Go backend in [`../backend`](../backend), running on **MySQL 8**. Same REST API
(`/api/v1/...`), same cookie-JWT + CSRF contract, so the existing frontend works unchanged. Design docs still live in
[`../backend/docs/`](../backend/docs/) (they describe PostgreSQL; the schema here is the MySQL translation).

## Stack

| Concern | Choice |
|---|---|
| Runtime / language | Node 20+, TypeScript (ESM) |
| HTTP | Fastify 5 (`@fastify/cors`, `@fastify/cookie`, `@fastify/rate-limit`) |
| DB | MySQL 8.0+ via `mysql2`, hand-written SQL in repositories |
| Migrations | plain SQL in `migrations/`, applied by `src/db/migrate.ts` (`schema_migrations` table, advisory lock) |
| Auth | HS256 JWT in `gym_session` httpOnly cookie; signed double-submit CSRF (`gym_csrf` cookie + `X-CSRF-Token`) |
| Validation | `zod` -> `400 VALIDATION_FAILED` with `details.fields` |
| Scheduler | `cron-parser` + timers, with `scheduled_job_runs` boot catch-up (Asia/Kolkata) |
| Tests | `vitest` against a real throwaway MySQL (`mysql-memory-server`) |

## Architecture

Every feature module is layered; dependencies point one way: `routes -> controller -> service -> repository`.

```
src/modules/<feature>/
  <f>.routes.ts       route table: path + method + permission -> controller action
  <f>.controller.ts   HTTP adapter: parse/validate request, call service, set status. No business rules.
  <f>.service.ts      business rules, transactions, audit logging, error mapping. No SQL, no HTTP types.
  <f>.repository.ts   ALL SQL for the module. No business rules. Takes an optional tx executor.
  <f>.model.ts        Row types (snake_case DB shape), Response types (API shape), mappers
  <f>.schemas.ts      zod request schemas + inferred input types
  index.ts            composition root: repository -> service -> controller -> routes
```

Cross-cutting: `src/plugins/errorHandler.ts` is the single place errors become HTTP responses (services throw
`AppError` from `src/common/errors.ts`; zod and body-parse errors are mapped there too); `plugins/auth.ts` (JWT +
permissions), `plugins/csrf.ts`, `common/audit.ts`, `common/codegen.ts` (MEM-001 style codes), `common/scheduler.ts`.

## MySQL notes (differences from the PostgreSQL original)

- Ids are `CHAR(36)` UUIDs generated by the app (`newId()`); no `RETURNING`, so repositories insert then re-select.
- Enums are inline `ENUM(...)` columns; timestamps are `DATETIME(3)` in UTC; `DATE` is read as `YYYY-MM-DD` strings.
- Partial unique indexes (one ACTIVE membership / trainer assignment per member) and the IST daily notification dedupe
  are emulated with stored generated columns + unique indexes.
- `MEM-001` style codes come from the `code_sequences` counter table (MySQL has no sequences).
- `chk_dob_past` is enforced in the service only (MySQL forbids `CURRENT_DATE` in CHECK constraints).
- Text search uses `LIKE` under the default case-insensitive collation `utf8mb4_0900_ai_ci`.
- Backups use `mysqldump` / `mysql` (override with `MYSQLDUMP_BIN` / `MYSQL_BIN`, or `docker exec` mode).

## Run

```bash
cp .env.example .env            # edit secrets and DATABASE_URL (mysql://user:pass@host:3306/db)
npm install
npm run build && npm run migrate
SEED_EMAIL=owner@example.com SEED_PASSWORD='ChangeMe123!' npm run seed
npm run dev                     # tsx watch, http://localhost:8080
```

### Tests

`npm test` downloads and starts a real MySQL 8.4 once (cached) — no Docker needed. On Linux it needs the shared
libraries `libaio` and `libnuma` (`sudo apt install libaio1t64 libnuma1`). Without root, extract the two `.deb`s to a
directory and set `LD_LIBRARY_PATH` to it.

### Docker

From the repo root: `docker compose -f docker-compose.fastify.yml up --build` (MySQL + this backend + frontend; a **new**
database volume — the original `docker-compose.yml` still runs the Go backend on PostgreSQL). Seed with
`SEED_EMAIL=... SEED_PASSWORD=... docker compose -f docker-compose.fastify.yml --profile seed up seed`.
